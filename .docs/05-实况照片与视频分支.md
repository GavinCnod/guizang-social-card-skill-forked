# 实况照片与视频分支

本文讲透 skill 里 Live Photo（实况照片）这一条动态卡分支：把用户视频装进社交卡版式，输出 `JPG + MOV + .pvt` 三件套。它不是长视频正片剪辑，也不是 Agent 主动去网上扒公开素材做的演示图；它的目标是把一段"已经被动作证明的现场"塞进一张小红书 / 微信公众号文章内能正常显示的 3:4 卡。读 `references/live-photo-production.md` 之前，先把这条分支的边界、平台口径、信息预算、版式选择、首帧先行原则、渲染与打包命令链、交付清单、失败模式、降级方案这十件事定清楚。

---

## 1. 分支定位与边界

### 1.1 什么时候走 Live Photo 分支

`SKILL.md` Step 1 Intake 给的触发条件很明确：用户**显式**说"Live Photo / 实况照片"，或者要求把视频素材做成社交卡、且动作本身就是证据（代码生成、UI 交互、游戏 demo、前后状态变化、滚动揭示、产品交互过程）。

参考 `references/live-photo-production.md:24-30`：

- 默认输入是**用户提供的视频**：录屏、产品演示、游戏画面、拍摄片段。
- **网络公开视频只用于自家 demo / 宣传案例**，或在用户明确要求使用素材示例时。
- 这条分支的核心是"证明一个瞬间、一段小过程、一个前后变化、或一组并列结果"，不是讲完整长故事。

### 1.2 什么时候不要接

下列情况 Live Photo 不是合适的目标，agent 应该直接 push back 或换路线：

| 场景 | 原因 | 推荐替代 |
| --- | --- | --- |
| 长视频正片剪辑（1-3 分钟成片、教程视频、配音解说） | `3s/5s` 装不下叙事，需要音频、章节、字幕 | 换成短链视频 / GIF / 公众号正文视频 |
| 需要精确"高光自动检测"的视频 | skill 不承诺精确自动检测，只能做"低成本诊断" | 让用户自己指定时间段，或先做 contact sheet 让用户挑 |
| 用户没给视频、想用 AI 生图做"动态卡" | Live Photo 是视频井，不是 GIF / 动效图 | 退回到普通静态卡，或改用 GIF / 短 MP4 fallback |
| 需要解释性字幕、解说词、教程步骤 | 单条 Live Photo 信息预算有限 | 拆成图文轮播，或用 21:9 + 1:1 公众号封面对 |

### 1.3 命名红线：观众视角 vs 制作视角

`references/live-photo-production.md:32` 明确要求：**观众看到的 H1、主标题、正文里不能出现制作术语**。`3s`、`5s`、`Live Photo`、`triple collage`、`long-video intake`、`information budget`、`speed-up`、`highlight detection`、`one action point` 这些词只能用在规划笔记、文件名、QA 摘要、交付文案里。

理由很直接：观众的卡应该像"他替自己发的"，不像"agent 在解释怎么做的"。渲染前要把每条观众可见的标题当读者读一遍，凡是听起来像任务要求的，全部替换成场景文案。

## 2. 平台与时长限制

### 2.1 两个平台的口径差异

| 平台 | 时长上限 | 画布 | 主要上传路径 | 备注 |
| --- | --- | --- | --- | --- |
| 小红书 / Rednote | `5s` | `1080 x 1440`，`3:4` | iPhone 端 App，发布时小红书会把它当 Live Photo 处理 | 也可桌面端上传，但 Live Photo 体验主要依赖 iPhone 路径（见 `references/platform-specs.md:27-33`） |
| 微信公众号文章内 Live Photo | `3s` | `1080 x 1440`，`3:4` | iPhone 端公众号文章编辑器；网页端没有 Live Photo 入口 | 桌面 / 网页发布时降级为 GIF 或短 MP4（见 `references/platform-specs.md:113-122`） |

### 2.2 时长背后的硬约束

`references/live-photo-production.md:79-82` 和 `references/live-photo-production.md:540-549` 列了具体规格：

- 帧率：屏幕录制 `24-30fps`，简单动态图 `12-15fps`。
- 编码：H.264 MOV，像素格式 `yuv420p`。
- 容器：`.mov`，配合 `-movflags +faststart`。
- 公众号文章内 Live Photo 必须 `<= 3s`，超过会丢 Live Photo 行为。
- 来源时长 < 目标时长时：**禁止静默用末帧 padding 当作"动态"**，必须明确告知 hold / slowdown，或换成更短的目标时长，或问用户拿更长的素材。

### 2.3 上传路径差异

| 平台 | 推荐发布路径 | 桌面 / 网页能不能发 |
| --- | --- | --- |
| 小红书 | AirDrop `.pvt` 到 iPhone → iPhone 小红书 App 发布 | 不建议作为主路径；`.pvt` 在桌面端多被识别为未知包 |
| 微信公众号文章内 | AirDrop `.pvt` 到 iPhone → iPhone 公众号文章编辑路径上传 | 网页端没有 Live Photo 入口，只能用 GIF / MP4 替代 |

`references/live-photo-production.md:482-508` 和 `references/platform-specs.md:113-122` 都重复了这条提醒：电脑端 `.pvt` 通常会被识别成未知包或拆成多个文件。

## 3. 信息预算（Information Budget）

### 3.1 时长承载的信息量

`references/live-photo-production.md:101-111` 给出 5 个格式的对照表：

| 格式 | 时长预算 | 最适合承载 | 避免 |
| --- | --- | --- | --- |
| 微信公众号单条 Live Photo | `3s` | 一个动作点、一次轻点结果、一个前后揭示 | 多步教程、长滚动、三个不相关片段 |
| 小红书单条 Live Photo | `5s` | 一段小过程、短产品交互、关键游戏操作、生成 → 结果证据 | 完整故事弧、密集解说、结果前冗长铺垫 |
| 三连 Live Photo 拼图 | 每个 `3-5s`，三个视频井同卡 | 三个并列结果、三个视角、三个例子、错误 → 修复 → 结果 | 顺序叙事（必须按 1-2-3 读的故事） |
| Material-first 拼图 | `3-5s` | 单 / 二 / 三 / 四宫格拼图，画面本身是内容 | 强加解释性文字、标签、示意图 |
| 长源视频 | 源远大于目标 | 诊断、裁切、倍速、拆分、用户指定时间窗 | 把整段硬压进 `3s/5s` |

### 3.2 动作角色词汇

`references/live-photo-production.md:113-119` 给出 5 种"动作角色"。一条视频大概率只承担其中一种，如果同时承担两种，要么挑最强的，要么拆。

| 角色 | 含义 |
| --- | --- |
| Operation proof（操作证据） | 准确呈现一次动作及其结果状态 |
| Process compression（过程压缩） | 从起始到结果的小型转化 |
| Before/after（前后对比） | 通过过渡让差异可信 |
| Parallel evidence（并列证据） | 多结果并排呈现 |
| Atmosphere supplement（氛围补充） | 静态卡承担信息，动效补场所 / 质感 / 真实感 |

### 3.3 视频井 ≠ 静帧序列

`SKILL.md` Step 5 Build And Render Live Photo 分支的最后一条硬约束原话（`SKILL.md` Non-Negotiables）：**禁止把视频卡伪装成静帧序列**。来源短于目标时长时只能选一种处理：问用户要更长素材、缩短目标时长、或显式标注 hold / slowdown，并在交付文案里写明。

## 4. 五种结构与版式

### 4.1 单视频动态卡

把一段视频裁成 `3:4` 吃满画布。需要文字时只放一组短标题，按 `M16 Image-Led Cover` / `image-overlay.md` 的主体避让、quiet-zone（安静区域：画面中相对稳定、不抢视觉的位置）、字体、局部 tint 规则处理（见 `references/live-photo-production.md:148-163`）。

硬规则：

- 源里自带的文字算素材，不要在上面再加新文字除非用户要求。
- 加文字时遵循 `image-overlay.md`：先做主体映射，禁止默认全图蒙版，只在安静区域放一行 Editorial serif / 宋体标题。
- 不要给单视频卡加序号、角标、徽章、刻度尺、字幕。

适合：咖啡冲煮、旅行片段、健身动作、产品状态、游戏关键操作。

### 4.2 二宫格 / 三宫格 / 四宫格拼图（material-first puzzle）

高质量素材自己说话时使用（见 `references/live-photo-production.md:144-163`）：

| 版式 | 几何 | 是否加文字 | 适合 |
| --- | --- | --- | --- |
| 单视频满铺 | 一段视频吃满 `3:4` 画布 | 至多一行短标题 | 咖啡 / 旅行 / 健身 / 产品 / 游戏瞬间 |
| 二宫格 | 上下两段 `3:4` 视频 | 默认不加 | 风景 / 穿搭精选 / 空间细节 / 菜品过程 |
| 三宫格 | 三段 `3:4` 视频垂直堆叠 | 不加文字 | 多步骤场景的高密度并置 |
| 四宫格 | `2 x 2` 四个 `540 x 720` 视频井 | 不加文字 | 高质量素材集的紧凑展示 |

硬规则：

- 沟槽 `0-12px`；用户明确要纯拼图或素材已有强边缘时选 `0`。
- 主体保护：人物要保住脸和上半身，物体要保住焦点特征；裁切保不住主体就换几何而不是硬裁。
- 每个视频井都要做 contact sheet 再选裁切位置。

### 4.3 三连 Live Photo 拼图

`references/live-photo-production.md:123-141` 给出三种结构和五种语义关系：

三种结构：

1. 纯三列 / 三条视频拼图，几乎不加文字，靠画面本身承担内容。
2. 顶部一行钩子标题 + 三个标注视频井，适合小红书首卡。
3. 编辑混合拼图，不对称井 + 标签 / 短结论 / 数字编号，适合教程、攻略、产品更新。

五种语义关系：

| 关系 | 含义 | 标签示例 |
| --- | --- | --- |
| Parallel comparison（并列对比） | A / B / C | `01 / SETUP` `02 / ACTION` `03 / RESULT` |
| Process stages（过程阶段） | before / during / after | `前` `中` `后` |
| Result showcase（结果展示） | 三个生成 / 测试输出 | `01 / 3D GAME` `02 / AI SITE` `03 / TRAVEL` |
| Correction flow（修正流） | 错 / 修 / 结果 | `错误` `修复` `结果` |
| Multi-view（多视角） | 全景 / 细节 / 结果 | `全景` `细节` `结果` |

硬规则：

- 不要把三连拼图变成三个迷你全屏录屏；每个井必须按证据区裁切。
- 标签要短，不要塞解释性长句。
- 静态关键帧（key photo）必须即使在动效不播放时也能独立成立。

### 4.4 长视频"低成本诊断"

针对用户给了一段 1-3 分钟甚至更长的素材，但没说要哪一段。`references/live-photo-production.md:165-195` 给出流程：

| 步骤 | 动作 |
| --- | --- |
| 1 | `ffprobe` 探测时长、分辨率、帧率、是否有音轨 |
| 2 | 生成稀疏 contact sheet（初扫 `8-12` 帧，候选 5 秒窗口 `12-15` 帧，候选 3 秒窗口 `8-12` 帧） |
| 3 | 只检查 contact sheet，不深入逐帧（除非用户明确要求） |
| 4 | 只识别"黑屏 / 空白开场 / 静止段 / 大段切换 / 可见结果帧 / 多段分离"这类粗结构 |

诊断完后给 5 种推荐里的一种：

| 推荐 | 适用 |
| --- | --- |
| Trim（裁切） | 一段稳定的时段，原速即可 |
| Speed-up + trim（倍速 + 裁切） | 想保留更多过程，可读性仍可接受 |
| Split / triple collage（拆分 / 三连） | 多段并列时刻比压缩一整段更合适 |
| Ask for range（请用户给时段） | contact sheet 看不出用户想要哪段 |
| Reject Live Photo（拒绝 Live Photo） | 素材需要解说、音频、长序列，建议改短链视频 / GIF |

参考回复模板（`references/live-photo-production.md:189-195`）：

```text
我先粗看了这个视频的信息量。它不适合整段压进 5 秒。
建议有两种：
A. 裁 00:04-00:09，保留关键操作和结果
B. 拆成三连 Live Photo：准备 / 操作 / 结果
你想走哪一种？
```

### 4.5 视频当图片井使用（Video As Image-Well Replacement）

`references/live-photo-production.md:310-324` 把视频井类比图片井：

- 保持原卡布局、边距、标签、字体、风格模式不变。
- 用同样的裁切逻辑对待视频。
- 视频首帧必须像一张合格的静态卡图片：UI / 文字 / 产品 / 细节不能被过裁，crop 符合原图片井规则和安全区，卡片在动效失效时仍能当静态图用。
- ffmpeg 里用 `crop` 先裁后 `scale` 模拟 CSS `object-fit: cover`；要保留密集 UI 文字可读性时用 `scale` + letterbox / 放大井位模拟 `object-fit: contain`。
- "可图性提升"（放大、清晰化、慢放、放大井位）是**选项而非自动修复**；用户没明确焦点优先级时，建议并等待。

## 5. 长视频诊断流程（ffprobe + contact sheet）

### 5.1 探测时长、分辨率、帧率

`references/live-photo-production.md:744-749` 给出的探针命令：

```bash
ffprobe -v error \
  -show_entries format=filename,duration,size \
  -show_entries stream=index,codec_type,codec_name,width,height,r_frame_rate,duration \
  -of json "source.mp4"
```

对每段用户视频都要跑一次。输出用于判断是不是长源（> 目标时长）、分辨率够不够做裁切、帧率是不是预期范围。

### 5.2 生成稀疏 contact sheet

通用命令模板（`references/live-photo-production.md:367-370`）：

```bash
ffmpeg -y -ss <start_seconds> -t <window_seconds> -i input.mov \
  -vf "fps=<frame_count>/<window_seconds>,scale=320:-1:flags=lanczos,tile=<cols>x<rows>:padding=12:margin=12:color=white" \
  -frames:v 1 contact-sheet.jpg
```

3 秒微信与 5 秒小红书示例：

```bash
# 3 秒微信 Live Photo，9 帧
ffmpeg -y -t 3 -i IMG_LIVE.MOV \
  -vf "fps=9/3,scale=320:-1:flags=lanczos,tile=3x3:padding=12:margin=12:color=white" \
  -frames:v 1 contact-wechat.jpg

# 5 秒小红书 Live Photo，15 帧
ffmpeg -y -t 5 -i IMG_LIVE.MOV \
  -vf "fps=15/5,scale=320:-1:flags=lanczos,tile=5x3:padding=12:margin=12:color=white" \
  -frames:v 1 contact-xhs.jpg
```

帧数选择规则（`references/live-photo-production.md:172-178`）：

- 长源初扫：`8-12` 帧。
- 候选 5 秒窗口：`12-15` 帧。
- 候选 3 秒窗口：`8-12` 帧。

仓库自带的封装脚本 `scripts/make-video-contact-sheet.py`（83 行）把同一逻辑包成 CLI：

```bash
python scripts/make-video-contact-sheet.py IMG_LIVE.MOV contact-xhs.jpg --frames 15 --cols 5 --duration 5
```

支持参数：`--frames`、`--cols`、`--start`、`--duration`、`--thumb-width`、`--padding`、`--margin`、`--color`。脚本会自动用 `ffprobe` 探源时长，再用 ffmpeg tile。

### 5.3 contact sheet 上要看的几件事

`references/live-photo-production.md:357-362` 列出检查项：

- 首帧是否过裁。
- 是否跨段落 / 跨分页边界。
- 计数器或 UI 文字是否清晰。
- 短片段是否被 padding 冻成静止。
- 是否出现意外黑边或长宽比变化。

## 6. 首帧先行原则（Preview-First Workflow）

### 6.1 为什么必须先做静态预览

`references/live-photo-production.md:326-342` 强调：昂贵动效路径只能在布局 / 裁切确认之后跑。视频第一帧要先在最终卡里成立，再生成 `.pvt`。这条规则在 `SKILL.md` Step 5 和 Non-Negotiables 都被反复点名。

### 6.2 首帧抽取命令

```bash
ffmpeg -y -ss <start_seconds> -i source.mp4 \
  -frames:v 1 -q:v 2 assets/source-first-frame.jpg
```

把这一帧当作用户提供的图片，按 `3:4` 静态卡版式正常渲染，套用相同的裁切、object position、标题间距、安全区、密度规则。

### 6.3 首帧要过哪些检查

`references/live-photo-production.md:316-323`：

- 重要 UI / 文字 / 产品 / 细节没被过裁。
- crop 符合原图片井规则与安全区。
- 周边标题 / 正文 / 布局仍然匹配所选版式。
- 即便动效不支持，卡片本身也能当静态图用。
- 抽取 key JPG 时，**优先选可读且强代表性的帧**，但必须和确认过的 crop 与构图一致。

### 6.4 从渲好的 MOV 抽关键帧

`references/live-photo-production.md:413-418`：

```bash
ffmpeg -y \
  -ss 2.7 -i IMG_TEST_LIVE_RAW.mov \
  -frames:v 1 -q:v 2 \
  IMG_TEST_LIVE.JPG
```

`-ss` 选一个既体现动作结果又不卡在切换边缘的时间点。

## 7. 渲染与打包命令链

### 7.1 总体流程

`references/live-photo-production.md:392-430` 给出从合成 MOV → 抽关键帧 → 打包 `.pvt` 的标准流水线：

1. `ffmpeg` 把多段源视频、背景、文字 / 边框 PNG 合成为 `1080 x 1440` 的 `IMG_RAW.mov`。
2. 用 `ffmpeg` 从 `RAW.mov` 抽一个强代表帧为 `IMG.JPG`。
3. 把 `RAW.mov` 重命名 / 复制为 `IMG.MOV`。
4. `makelive` 把 `JPG + MOV` 打包成 `.pvt`。
5. `ffprobe` 验证尺寸、时长、帧数；`plutil -p` 检查 `metadata.plist`。
6. `scripts/make-video-contact-sheet.py` 生成 contact sheet 做视觉抽检。

### 7.2 把多段视频合成 3:4 MOV 的示例

`references/live-photo-production.md:396-405`，把三段横屏录屏合成一张 `3:4` Live Photo 源片：

```bash
ffmpeg -y \
  -ss 145 -t 3 -i "Area测试 01.mp4" \
  -ss 49 -t 3 -i "Area 测试 2.mp4" \
  -ss 154 -t 3 -i "Area 测试 3.mp4" \
  -i overlay.png \
  -filter_complex "color=c=0x030611:s=1080x1440:d=3:r=15[bg];[0:v]fps=15,crop=1580:980:344:60,scale=1000:330:force_original_aspect_ratio=increase,crop=1000:330,setsar=1[g];[1:v]fps=15,scale=1000:330:force_original_aspect_ratio=increase,crop=1000:330,setsar=1[a];[2:v]fps=15,scale=1000:330:force_original_aspect_ratio=increase,crop=1000:330,setsar=1[s];[bg][g]overlay=40:190[p1];[p1][a]overlay=40:590[p2];[p2][s]overlay=40:990[p3];[p3][3:v]overlay=0:0" \
  -t 3 -r 15 -an -c:v libx264 -pix_fmt yuv420p -movflags +faststart \
  IMG_TEST_LIVE_RAW.mov
```

要点：

- 画布 `1080 x 1440`，`3:4`，用 `color` filter 当底。
- 每段视频 `fps=15` 锁帧率，再 `crop` + `scale` 落井。
- 顶部 / 中部 / 底部三段用 `overlay` 摆位。
- 输出 `-movflags +faststart` 让 AirDrop / 移动端播放器更快起播。
- 缺 `drawtext` 时用 ImageMagick 出透明 PNG，再用 `overlay` 叠。

## 9. 失败模式与禁忌

### 9.1 MIMO 案例总结的失败模式表

`references/live-photo-production.md:804-814`：

| 失败现象 | 大概率原因 | 修法 |
| --- | --- | --- |
| 结果区看起来像两段视频重叠 | crop 太浅，源页跨了段落边界 | 把结果区拉高、保留完整垂直源、查 contact sheet |
| 结果区感觉冻结 | 短源被拉伸太多 | 改用更长 / 更晚的时间窗，或只裁不加速 |
| 数字读不清 | crop 把空白浏览器框带进来了，或源码率低 | 贴实真实平台计数器；必要时索取更高码率源 |
| token strip 失去"生成感" | crop 只看到数字面板 | 把数字上方一截生成的代码也带进来 |
| 5 秒输出播放但某区卡住 | 某源短于目标时长，或被 `tpad` 拉伸补帧 | 用真正 5 秒源，或显式标注 hold |
| iPhone 导入后变成两张图 | AirDrop 了松散的 `JPG` / `MOV` | 只 AirDrop `.pvt` 包 |
| 风格不像这个 skill | 卡片没遵守 Swiss 规则（off-white + 黑 + 单一 IKB 锚点、直角模块、无阴影 / 玻璃 / 圆角） | 用 off-white、黑、单一 IKB 锚点、直角模块、零阴影 |

### 9.2 文档明确点名的几条禁忌

来自 `SKILL.md` Non-Negotiables 与 `references/live-photo-production.md` 全文：

| 禁忌 | 文档位置 |
| --- | --- |
| 跳过首帧预览直接渲 `.pvt` | `SKILL.md` Step 5 Live Photo branch |
| 在浅 crop 里让结果视频跨段滚动，制造"两段视频叠在一起"的错觉 | `SKILL.md` Non-Negotiables |
| 用户没明确焦点时擅自猜裁切优先级 | `SKILL.md` Non-Negotiables |
| 来源短于目标时长时静默 padding 装作"动态" | `SKILL.md` Non-Negotiables；`references/live-photo-production.md:285-288` |
| 把松散 `JPG + MOV` 当 Live Photo 直接 AirDrop，会被识别成两张图 | `references/live-photo-production.md:46-49` |
| 在观众可见的 H1 / 主文案里塞 `3s` / `5s` / `Live Photo` / `triple collage` / `long-video intake` / `information budget` / `speed-up` / `highlight detection` / `one action point` 这些制作术语 | `references/live-photo-production.md:32` |
| 加模板填充物：标签、数字标、刻度、徽章、字幕、解释性生产文案 | `references/live-photo-production.md:155-157` |
| 用 `scale + force_original_aspect_ratio=increase` + 紧垂直 crop 强行变节奏，会让滚动看起来错位 | `references/live-photo-production.md:693-696` |

### 9.3 焦点 / 时长不明确时的标准提问模板

来源短于目标时长（`references/live-photo-production.md:294-299`）：

```text
这个素材短于目标 Live Photo 时长。你想：
A. 换一个更长素材
B. 直接做成较短的 Live Photo
C. 允许末帧停住 / 轻微慢放，并在交付时说明
```

焦点 / 裁切不确定（`references/live-photo-production.md:303-308`）：

```text
这个视频可以有两种处理：
A. 放大关键区域，数字 / UI 更清楚，但会少一点全局上下文
B. 保留完整画面，信息更全，但手机上细节会小一些
你更想突出哪一个？
```

长源诊断后的标准回复（`references/live-photo-production.md:189-195` 和 `references/live-photo-production.md:278-283`）：

```text
我先粗看了这个视频的信息量。它不适合整段压进 5 秒。
建议有两种：
A. 裁 00:04-00:09，保留关键操作和结果
B. 拆成三连 Live Photo：准备 / 操作 / 结果
你想走哪一种？
```

## 10. 降级方案

### 10.1 何时降级

`SKILL.md` Step 7 Deliver 明文：当用户没法走 iPhone / AirDrop 路径（纯桌面工作流、Android 设备、不支持 Live Photo 的平台）时，agent 应给出降级交付。

### 10.2 降级产物

从同一份 MOV 源导出：

| 产物 | 优势 | 损失 |
| --- | --- | --- |
| GIF 循环 | 桌面端能直接预览、跨平台 | 文件大、长 GIF 体积爆炸、画质损失 |
| 静音 MP4 短片 | 兼容所有现代浏览器和编辑器 | 失去 Live Photo "长按播放" 的原生体验 |

静态 `3:4` JPG 仍然保留作为兜底图（即使动效播放失败也能用）。

### 10.3 降级时的沟通

- 主动告诉用户这会失去 Live Photo 的原生交互。
- 询问是否走降级再切换，不要自作主张。
- 降级产物和 Live Photo 产物放在同一输出目录，命名区分（如 `IMG_<slug>_LIVE_FALLBACK.gif` 或 `IMG_<slug>_LIVE_FALLBACK.mp4`）。

## 12. 复用检查清单（来源：MIMO 案例）

`references/live-photo-production.md:816-826` 给出的 8 步复用规则，针对"屏幕录制型 Live Photo"：

1. 先查源时长、分辨率、码率。
2. 先做 contact sheet 再选 crop。
3. 先渲静态预览再打 `.pvt`。
4. 让结果 / demo 区当主要视觉证据。
5. 过程 / token 区保留小但清晰。
6. 保留真实 UI 计数器，不造装饰 KPI。
7. 渲染后用帧数验证时长是真的。
8. `.pvt` 包给 AirDrop 测试用。

凡是屏幕录屏类素材，按这 8 步走能避开绝大多数已知失败模式。
