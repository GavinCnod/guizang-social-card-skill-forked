# 01 · 能力与适用边界

这份文档回答"这个 skill 到底能做什么、做出来是什么样、什么请求应该直接拒绝"。它是对 `SKILL.md` 的"输入 / 输出 / 边界"抽象，不涉及具体视觉规则（那些在 `03`、`04`、`05`）。

---

## 一、要解决的真实问题

`PRODUCT.md` 把问题定义得很直接：**真正的痛点不是"画图"，而是"把一篇文章变成一组能打的小红书图"**。

普通用户的现实链路是：写完一篇文章 → 想要 5-9 张图 + 1 张封面 → 没有设计师、没时间在 Canva / Figma 里逐张拉 → 用模板套又被几百个相似封面挤掉点击 → 让 AI 出图，结果都是"标题居中 + 渐变背景 + 一个 emoji"。

这个 skill 插在第 2-5 步之间，追求的是三件事同时成立：

| 目标 | 含义 | 反面 |
| --- | --- | --- |
| 质量 | 像"被偏爱的杂志"，不是 PPT 模板 | 信息图横幅感、SaaS 卡片拼盘 |
| 效率 | 30 分钟内拿到可发布的图 | 在 prompt 上反复打磨 |
| 不假 | 数据、报价、版本号不编；文字不压到人脸上 | 假数据、标题压脸 |

其中**质量是分水岭**：Canva 已经解决了效率，AI 出图已经解决了速度，但都没解决"看一眼就知道是用心做的"。

## 二、能力清单

### 2.1 四类可交付产物

| 产物 | 触发说法 | 画板 / 尺寸 | 交付形态 |
| --- | --- | --- | --- |
| 小红书组图 | "做一套小红书图文 / Rednote 卡片 / 3:4 封面" | `.poster.xhs` 1080×1440 | 多张 PNG |
| 公众号封面对 | "公众号 21:9 头图 + 1:1 分享卡" | `.poster.wide` 2100×900 + `.poster.square` 1080×1080 | 2 张 PNG，同一 HTML 内成对构建 |
| 静态封面 / 配图 | "文章封面 / 产品更新卡 / 教程拆页 / 截图说明图" | 上述三种画板任选 | 单张或多张 PNG |
| Live Photo 动态卡 | "Live Photo / 实况照片 / 三连实况拼图 / 四宫格拼图" | 复用社交卡比例 | `JPG + MOV`，打包成 `.pvt` |

### 2.2 内容输入的接受范围

`SKILL.md` 的 description 与 Step 1 明确列出可接受的输入：**文章、脚本、产品笔记、字幕、截图、照片、用户提供的视频**。

其中两类需要特别处理：

- **截图 / 图片**：属于"证据层"。News / Tutorial / Data / Review 类内容会被**主动追问截图或照片**，因为没有真实物料的封面会被读成填充物。
- **视频**：只在用户主动要求 Live Photo 时进入动态分支；用户提供视频是正常路径，网上下载的免费视频只用于内部 demo / promo / 回归测试。

### 2.3 三套视觉系统（能力层面的差异）

| 系统 | 视觉特征 | 读起来的感觉 |
| --- | --- | --- |
| Editorial Magazine × E-ink | Serif/宋体 display + 安静的无衬线正文、纸与墨的色板、氛围层（纸纹 / 墨洗 / WebGL 画布）、ledger 账本行、marginalia 边注、pull quote、大幅图井 | 慢、被认真编辑过、手工排的 |
| Swiss International | Inter / Helvetica 感、超大字号但极细字重、小号等宽标签、严格左对齐网格、发丝线、单一高饱和锚点色、card-fill 矩阵 / KPI 塔 / H 条形图 / 编号陈述 | 工程化、可量化、有决断力 |

关键规则（v0.10 起，v0.16 扩到三套，见 `PRODUCT.md` 决策 1）：**三套系统是视觉立场，不是内容类型门**。职场随笔可以走 Editorial，旅行账本可以走 Swiss，品牌盛典可以走 Warm Gold；选风格按"想让它读起来什么节奏"，不按品类查表。同一套图里禁止混用系统，除非用户明确要求 hybrid。

| Editorial | Dune 沙丘 | `#1f1a14` / `#f0e6d2` | 艺术、设计、时尚 |
| Editorial | Midnight Ink 午夜墨 | `#0e0d0c` / `#ece2cf` / `#d4a04a` | 游戏 key art、夜景、影调封面 |
| Swiss | IKB 克莱因蓝 | `#002FA7` | 通用默认、AI 产品、方法论 |

### 2.5 版式骨架（40 个）

- Editorial `M01-M16`：叙事与氛围类骨架，含 M16 Image-Led Cover（满铺主图压字）、M07 Field Ledger（账本）、M11 Marginalia Essay（边注长文）、M14 Vertical Pipeline（纵向流程）等。
- Swiss `S01-S12`：数据与结构类骨架，含 S09 KPI Tower、S10 H-Bar Chart、Matrix + Hero 等。

骨架的作用是**先选后改**：不从零发明页面结构，也不为了"看起来设计过"而加模板里没有的装饰（kicker、meta、发丝线、刻度、徽章）。逐条的用途、文案上限与最低密度见 [`04-内容策划与版式骨架.md`](./04-内容策划与版式骨架.md)。

### 2.6 Live Photo 能力

| 版式 | 效果 | 适合 |
| --- | --- | --- |
| 单视频动态卡 | 一段视频裁成 3:4 吃满画布；需要文字时按 `M16 Image-Led Cover` / `image-overlay` 规则压字 | 咖啡、旅行、健身动作、产品状态、游戏瞬间 |
| 二 / 三 / 四宫格拼图 | 多个视频井拼成一张 Live Photo，通常不加文字 | 旅行风景、穿搭精选、空间细节、菜品过程 |
| 三连 Live Photo 拼图 | 三段几秒素材并列，提高短时长内的信息密度 | 攻略步骤、前后对比、多视角、模型测试结果 |
| 长视频诊断 | 稀疏抽帧 / contact sheet，判断该裁哪段、倍速、拆分，还是请用户指定时间段 | 用户给了 1-3 分钟素材但还没选片段 |
| 平台发布包 | 调试用 `JPG + MOV`，iPhone 测试 / 发布用 `.pvt` | 小红书、公众号文章内 |

平台时长：**小红书按 5s，微信公众号文章内按 3s**（微信公众号的 Live Photo 必须从 iPhone 上传）。发布通常要走手机端路径（`.pvt` AirDrop 到 iPhone 后从对应 App 发布），电脑端 / 网页端一般不能把 `.pvt` 识别为可发布 Live Photo；用户无法走该路径时，可降级为循环 GIF 或静音 MP4。

### 2.7 图源能力（用户没图时）

v0.7 起 Step 1 有"三选一"入口，用户只给文字时问一次：

```text
这篇我需要 1-2 张图。三种走法：
A. 你自己有照片 / 截图，传给我（推荐——最不"AI"感）
B. 我去 Pexels / Unsplash / Flickr 帮你找
C. 用 AI 生成
```

规则是**一次性提问**：推荐 A 一句话，用户选什么就做什么，之后不许再劝，也不许悄悄把 B/C 当成默认。

若走 B，可用图源（全部免版权费图库，不接视觉中国 / Getty / 站酷海洛）：

| 顺序 | 图源 | 优势 |
| --- | --- | --- |
| 1 | Pexels | **原生支持中文关键词**，补国内场景缺口 |
| 2 | Unsplash | 户外 / 生活方式 / 氛围底图 |
| 3 | Flickr CC（`license=2,3,4,5,6,9`） | 纪实真实感：街拍、人物在场景中、真实室内 |
| 4 | Wallhaven | 游戏 / 动漫 / 壁纸题材 |
| 5 | 直接搜索 | 特定主体（产品渲染、游戏剧照、历史照片） |

取图后必须：落本地 `assets/`、按用途命名（`hero-mountain.jpg` 而不是哈希名）、把来源写进 `assets/SOURCES.md`，并把来源**先告知用户**再决定是否在图上标注。Swiss 模式极少需要图库——产品渲染、UI 截图、keyshot 风格图应由用户提供或 AI 生成。

### 2.8 截图美化资产

`assets/screenshot-backgrounds/` 提供 13 张真实材质 WebP 底（Editorial 5 张 / Swiss 4 张 / Warm Gold 4 张），配套 `.frame-shot`、`.device-browser`、`.device-phone` 工具类。Swiss 的材质底**强绑定 accent**（`bg-asset-ikb-dot` 只能配 `data-accent="ikb"`），且不允许在材质底上叠 `shadow-ed` 描边。

## 三、能力边界：明确不做的

### 3.1 赛道级别的"不接"

| 不接的请求 | 原因 |
| --- | --- |
| 美食 菜品大片摆盘 | 依赖专业美食摄影，本 skill 不替代 |
| 穿搭 日常 OOTD 全身 | 不生成 / 模拟人像照片 |
| 情感 梦核 / 氛围感装饰风 | 与 Editorial / Swiss / Warm Gold 三套系统正面冲突 |
| Y2K / 千禧辣妹 / 哥特萝莉 / kawaii 装饰风 | 同上 |
| 纯摄影展示类帖子（图就是全部交付物） | 没有版式诉求 |

`SKILL.md` 的要求是：**在 Intake 阶段就说清做不了什么**，不要静默换一个不符合用户意图的版式硬交差。注意 `HANDOFF.md` 的"已知风险"里写明：这份品类能力圈**没有硬编码进代码**，skill 不会自动拒绝，需要执行者自己读到并主动告知。

### 3.2 任务类型的"不做"

- 横向翻页 PPT / 网页演示 → 用上游 `guizang-ppt-skill`
- 长视频正片剪辑 → 本 skill 只支持"短小、绑定版式"的 Live Photo 卡
- 无版式诉求的纯修图、纯文字编辑
- 自定义主题色 / 风格自定义（`PRODUCT.md` 中标注为"真的不做"）

### 3.3 反模式清单（`PRODUCT.md` 第 6 节归纳）

1. 不可读的小字（1080×1440 上正文低于 26px）
2. 大字号 + 重字重标题（Swiss 80-120px 配 weight 700）
3. 任意装饰 SVG（blob、雨滴、贴纸、随手画的圈）
4. 嵌套卡片 / SaaS 卡片拼盘
5. 裸跑图片压字（照片没有 quiet zone、标题压过主体、缩略图不可读）
6. 假数据 / 假版本号 / 假报价
7. 一图复用到所有比例（把 21:9 直接裁成 1:1）
8. 图上加教程说明（键盘快捷键、操作步骤压在卡面）

## 四、小红书 11 个品类的能力圈

`SKILL.md` 与 `references/category-cookbook.md` 把常见品类分三档：

**端到端强势**（文 / 结构 / 图都在能力圈内）

- 旅行 Travel、职场 Workplace、推荐 Recommended（需指定子类后）

**文与结构强势，图依赖用户或图库**

- 游戏 Game、影视 Film/TV、美食（食谱方向）、彩妆（教程方向）、健身 Fitness、家居 Home、穿搭（精选 / 胶囊衣橱方向）

**能力圈外，应主动说明而不是硬接**

- 美食 菜品大片摆盘、穿搭 日常 OOTD 全身、情感 梦核 / 氛围感装饰风、Y2K 系、纯摄影展示

> 文档间存在一处口径差异：`HANDOFF.md` 的"数据规模"表写作"11 个品类中 7 个完整支持，4 个需用户提供素材，4 个明确不接"，而 `SKILL.md` 的分档是"3 个端到端强势 / 7 个需供图 / 若干不接"。维护时以 `SKILL.md` 与 `category-cookbook.md` 为准，两者需要对齐。

## 五、触发方式

| 场景 | 说法示例 |
| --- | --- |
| 触发 skill | "帮我做一套小红书图文"、"做一套 Rednote 卡片"、"生成一套 social cards" |
| 公众号封面对 | "做一个公众号 21:9 头图 + 1:1 分享卡" |
| 指定风格 | "做一套瑞士风的小红书测评 / IKB 风格图文"、"标题用电子杂志风" |
| Live Photo | "把这段视频做成小红书 Live Photo"、"做一个微信公众号文章内 3 秒 Live Photo"、"三连实况拼图" |
| 教程 / 拆页 | "把这篇文章做成轮播图文 / 教程拆页" |

安装方式（fork 版）：`git clone -b dev-personal-usage-gavin https://github.com/GavinCnod/guizang-social-card-skill-forked.git ~/.claude/skills/guizang-social-card-skill-forked`（目录名与 skill 名一致，Agent Skills 规范要求 `name` 与父目录同名）。上游原版：`npx skills add https://github.com/op7418/guizang-social-card-skill --skill guizang-social-card-skill`。上游 README 也给出了"把安装指令直接发给有 shell 权限的 Agent"的方式。

平台支持（`README.md`）：Claude Code / Codex 支持；Cursor 等本地 Agent 需具备读写文件 + 执行 shell 的能力；普通 Chatbot 不推荐（没有文件系统与渲染管线时无法稳定出图）。

## 六、产出效果的判断标准

"效果"在这个 skill 里不是主观描述，而是被量化成可检查的门槛：

| 维度 | 门槛 | 依据 |
| --- | --- | --- |
| 3:4 画布填充 | 内容（文字 + 图 + 数据）覆盖 ≥75% 画布高度；>15% 的空白带必须有留白理由 | `SKILL.md` Non-Negotiables |
| 横带密度 | 1440 高切 4 横带，Filled + Justified 需 ≥100%、Filled ≥75%，相邻两带不能都靠"合理留白" | `references/qa-checklist.md`、校验器 R5 |
| 字号 | 正文不得低于手机可读下限；Swiss 大标题遵守"越大越细" | 校验器 R3 / R4 |
| 标题留白 | 主 display 标题下方 ≥28px，局部小标题 ≥16px | 校验器 R9 |
| 缩略图可读性 | 渲染 PNG 缩到 360px 宽后标题仍可读 | `references/image-overlay.md` |
| 溢出修正 | 1-40px 微调、40-90px 局部压缩、90-160px 轻微压缩标题或段落、160px+ 才考虑换骨架或减内容 | `SKILL.md` Non-Negotiables |
| 数据真实性 | 版本号、报价、百分比一律不得编造 | `PRODUCT.md` 反模式 6 |

校验脚本 `validate-social-deck.mjs` 用 Playwright 做真实 DOM 测量（不是静态扫描），覆盖溢出、footer 碰撞、Swiss 粗体 display、字号下限、4 横带密度、`.h-xl` 行数上限、figure 默认 margin 漂移、视觉边界与标题间距、金渐变面积、阴影色共 11 条规则（R1-R11）。**但按 Step 7 的规定，渲染完成后默认不自动跑**——先把图给用户看，问一句"你自己看还是我先自动核查"，用户要求才跑。
