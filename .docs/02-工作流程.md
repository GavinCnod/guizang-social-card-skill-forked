# 02 · 工作流程

`SKILL.md` 定义的是 **7 步主流程 + 1 个子步骤（Step 4.5）**。这份文档按 Agent 实际执行顺序拆解每一步的输入、动作、产出与硬约束，并标出"什么时候必须停下来问用户"。

流程的骨架是：

```text
Step 1 Intake          收集会改变结果的信息（平台 / 品类 / 素材 / 图源三选一）
Step 2 Extract Story   把原文变成页面计划（封面钩子 + 一页一个意思）
Step 3 Choose Style    选 Editorial 还是 Swiss，再选一套主题
Step 4 Plan Pages      写出每页的 hook / 文案 / 视觉证据 / 版式意图
Step 4.5 Seed          拷 assets/template-*.html 到任务目录当 index.html
Step 5 Build & Render  替换 POSTERS_HERE → Playwright 导出 PNG → 验证尺寸
Step 6 Image Handling  截图包装 / 文字压图 / 无图时的取图分支
Step 7 Deliver         先给用户看图，再问要不要跑自动校验
```

一次完整任务通常 3-9 张图，目标总耗时 30 分钟以内。

---

## Step 1 · Intake：只问会改变结果的问题

**动作**：从用户已有信息里推断，只补问缺失且会改变产出的项。`PRODUCT.md` 把这步的原则写成"不要审讯式提问"。

需要收集的项：

| 项 | 说明 |
| --- | --- |
| 目标平台与比例 | 小红书 3:4 / 公众号 21:9 + 1:1 / 朋友圈 / 视频号封面 |
| 源文本 | 文章、字幕、产品笔记、标题 |
| 小红书品类 | 用户说出 11 个常见品类之一时，走 `references/category-cookbook.md` 路由并确认是否在能力圈内 |
| 图片 / 截图 | 每张图打算放在哪一页。News / Tutorial / Data / Review 类内容要**主动索取**截图或照片，它们是证据层 |
| 视频素材 | 用户要求 Live Photo 时确认素材、平台、时长 |
| 风格倾向 | Swiss / 杂志风 / 科技 / 户外等 |
| 硬约束 | 必须出现的标题文字、1:1 封面不放图、必须包含硬件照片、截图必须可读等 |

**这一步的三个关键分流**：

1. **品类路由**。若请求落在能力圈外（菜品大片摆盘、OOTD 日常、梦核氛围等），要在设计之前就说清楚，不许静默换一个不符合意图的版式。
2. **无图三选一**。用户只给文字时，问一次：

   ```text
   这篇我需要 1-2 张图。三种走法：
   A. 你自己有照片 / 截图，传给我（推荐——最不"AI"感）
   B. 我去 Pexels / Unsplash / Flickr 帮你找
   C. 用 AI 生成
   ```

   推荐 A 只用一句话；用户选了什么就执行什么（包括"都行你看着办"）；**这是一次性问题，之后不许反复劝导**，也不许把 B / C 当成默认。
3. **Live Photo 视频 intake**。确认目标平台（小红书 5s / 公众号 3s）；先读 `references/live-photo-production.md`，把请求分类为单视频、三连拼图还是长视频 intake。若素材过长或包含多个可用瞬间，先做低成本诊断，再问一次"是修剪、倍速、拆成多个视频井，还是用你指定的时间段"。素材短于目标时长时，要问"提供更长素材 / 接受更短的 Live Photo / 明确允许 hold 或慢放"。重点区域不明确时，给出可能的裁切 / 放大方案让用户决定，不替他猜。

**事实核查**：内容涉及当前产品发布、政策、价格、声明或新闻时，用浏览工具核实不稳定事实，并在最终回复里给出处。

## Step 2 · Extract The Story：先有计划，再设计

把源内容变成**页面计划**，而不是直接开始排版。

**小红书**

- Page 1 是封面钩子。
- Page 2-N 每页只承载一个观点。
- 大多数帖子 5-9 页；下半区开始变空时就压缩或合并。
- 细节留给正文文案区；图片负责钩子、对比、清单和锐利的结论。

**微信公众号**

- 永远成对产出：`21:9` 主封面 + `1:1` 方封面。
- 两块封面写在**同一个 HTML 文件**里，并加一段合并预览区块，方便检查两者的视觉关系。
- `21:9` 保留完整或接近完整的标题、副标题和一个强视觉关系。
- `1:1` 使用由长标题推导出的短标题：大字居中、默认不放图、不塞拥挤的副标题（推导方法见 `references/title-shortener.md`）。

## Step 3 · Choose Style Mode：选立场，不选品类

**每个包只选一种模式**，不混用（除非用户明确要求 hybrid）。三套系统的差异见 [`03-视觉系统与主题.md`](./03-视觉系统与主题.md)。

选择逻辑（v0.10 起明确）：

- 三套系统**不与具体内容类型绑定**。职场随笔可以走 Editorial，旅行账本可以走 Swiss，节庆盘点可以走 Warm Gold。
- 决定因素是这个内容的"编辑意图"：**这是一篇特写，还是一份发布说明？还有它需要多少仪式感？** 特写 → Editorial；发布说明 / 数据 → Swiss；需要金色仪式感的盘点 / 榜单 / 年终 → Warm Gold。
- 主题只能从 16 套预设里选（Editorial 6 / Swiss 4 / Warm Gold 6），不允许自造颜色。

## Step 4 · Plan Pages：把每页写成一行

产出一份简洁的内部计划：

```text
Page 01 / cover / hook / image source / layout intent
Page 02 / point / key copy / visual evidence / layout intent
...
```

- 用户要求先审批时展示这份计划；否则内部使用并继续。
- 用 `references/layout-recipes.md` 选页面结构；避免每页都是"标题 + 卡片"的重复结构。
- 做 3:4 时先看 `references/portrait-fill.md`：短表格或账本必须被扩写成完整的竖版构图（引语列、图片证据、边注、更大的行、背景 hero 区）。
- **文案纪律**：面向观众的文案必须描述用户真实场景，不许把 `3s`、`5s`、`Live Photo`、`三连拼图`、`信息量`、`长视频 intake`、`倍速`、`高光检测` 这类内部制作词写成 H1、钩子或正文。渲染前要把每个可见标题当作真实读者再读一遍。
- **反装饰纪律**：不要为了满足自动密度警告而添加模板外的装饰（额外标尺、侧栏、伪时间轴、装饰标签、自造徽章）。密度警告要用"换更合适的骨架 / 调整真实内容尺寸 / 接受 advisory 并说明视觉理由"来解决。

**Live Photo 页的规划方式**：先当作普通社交卡规划，再决定运动角色——一个动作点、一个小流程、一个前后变化、三个并列结果，或纯氛围 / 证据。结构上唯一的变化是"一个或多个图片井变成视频井"，比例、裁切、安全区、字体、风格模式规则全部不变。首帧必须通过与静态图相同的检查。

## Step 4.5 · Copy The Seed Template：不许从零写 HTML

| 模式 | 拷贝的种子 | 拷成 |
| --- | --- | --- |
| Editorial Magazine × E-ink | `assets/template-editorial-card.html` | 任务目录下的 `index.html` |
| Swiss International | `assets/template-swiss-card.html` | 任务目录下的 `index.html` |

种子已经预置：字体加载、主题 token、三种画板尺寸（`.poster.xhs` / `.poster.square` / `.poster.wide`）、配对预览框架、颗粒与背景层，以及全部 layout recipe 会引用到的 class。

**设置主题**：

- Editorial：`<html data-theme="ink-classic | indigo-porcelain | forest-ink | kraft-paper | dune | midnight-ink">`
- Swiss：`<html data-accent="ikb | lemon-yellow | lemon-green | safety-orange">`

**填充页面**：把 `<!-- POSTERS_HERE -->` 之后的占位 poster 替换成每页一个 `<section class="poster ...">`，HTML 骨架从所选 recipe（Editorial `M01-M16` / Swiss `S01-S12`）里取。

> 硬约束：**不能加载错模板的 class 系统**。Editorial 的 recipe 假设 serif display + ledger / marginalia / pipeline-v；Swiss 的 recipe 假设 Inter + card-fill + matrix / h-bar / kpi-tower。混用会静默塌版。

## Step 5 · Build And Render

**默认实现模式**：

1. 在 `local-tests/<slug>/` 下建任务目录，或用户指定的输出目录。**禁止**把生成的任务目录、渲染图、MOV 文件、`.pvt` 包或下载的素材放在 skill 根目录。
2. 源图放 `assets/`。
3. 从 Step 4.5 拷来的种子开始改，优先只动 `<!-- POSTERS_HERE -->` 区域。需要自定义版式 CSS 时，在拷来的文件里加一段命名清晰的任务级样式块，并保留语义默认值重置（如 `figure { margin:0; }`），避免浏览器默认间距引起漂移。
4. 用 Playwright 或浏览器截图工具导出每个 `.poster` / `.cover` 节点。
5. 渲染图存到 `output/`。
6. 检查尺寸并查看渲染出的 PNG。
7. 随时可跑 `node validate-social-deck.mjs <task-dir>` 做自动检查：R1 溢出、R2 footer 碰撞、R3 Swiss 粗体 display、R4 最小字号、R5 4 横带密度、R6 `.h-xl` 行数上限、R7 figure 默认 margin 漂移、R8 视觉边界 / 底部空白、R9 标题与内容间距。任一条 FAIL 时退出码为 1，属于"自动检查被要求时必须先修"的项；WARN 是建议但需要读一遍。

**Live Photo 分支（同一步内）**：

1. 渲染前先定信息预算：`3s` 装一个动作点；`5s` 装一个小流程；三连拼图装三个并列片段，装不下复杂故事；长视频必须先诊断。
2. 长素材不做"精准自动高光检测"的承诺：探测时长分辨率、做稀疏 contact sheet，然后在修剪 / 倍速 / 拆分或三连 / 询问用户时间段之间选择。
3. 从每个视频井抽首帧放进最终静态卡版式，先给用户或自己看这个预览，再做 `.pvt`。这一步用极低的 token 与渲染成本拦住裁切和层级问题。
4. 按平台时长渲染配对 MOV：小红书 `5s`，公众号 `3s`。
5. 从可读的代表帧抽关键 JPG。
6. 用 `makelive` 把 `JPG + MOV` 打包成 `.pvt`；AirDrop 时作为一个整体发送用于 iPhone 测试。
7. 校验尺寸、时长、帧数、包内容与运动质量；视觉检查优先用 contact sheet 帧条，只需要人工 / 模型检查最终拼好的那张图。

**越界修正的纪律**（先量再改）：

| 溢出量 | 修正手段 |
| --- | --- |
| 1-40px | 轻推 / 收紧间距 |
| 40-90px | 局部压缩 |
| 90-160px | 轻微压缩标题或段落 |
| 160px+ | 才考虑换 recipe 或删内容 |

修完要复查 R8，避免从"溢出"荡到"下半屏一大片空白"。

## Step 6 · Image And Screenshot Handling

**用户提供截图时**：保留截图内容（除非用户要求重做）；优先程序化包装（目标比例画布、安全内边距、干净背景、可读截图）；不许拉伸截图；截图清晰度重要时，放大截图区域并减少周边文字。

**文字压在图上时**（满铺封面、大图井、生成图叠加），按 `references/image-overlay.md` 走：

1. **选图优先，只在必要时加 tint**。照片覆盖 ≥60% 画布时先过 quiet-zone 与 light 测试；**先不加遮罩构图**；缩略图检查失败时，才在标题区加局部、取自图片色调的 tint。禁止默认全幅渐变。
2. **主体映射是强制的**。放标题之前用 Read 工具读图，用平实语言描述主体脸部 / 焦点在哪，并把主体映射记录成 hero 区块旁的 HTML 注释。文字只能放在记录下来的安全区里。
3. **裁切纪律——每张图都 inline 写 `object-position`**。模板默认值 `center 50%` 是 fallback 不是推荐值；跳过这一步会在高比例画板（`r-3x4`、`r-21x9`）上静默把主体裁出画外。
4. **缩略图测试**。把渲染 PNG 缩到 360px 宽，确认标题仍然可读。标题与照片打架就移动标题、换图或加局部同色系 tint；照片看起来"死"了说明 tint 太重或这张图不适合压字。

**用户没有图时**：这条分支**只在 Step 1 的三选一落在 B 或 C 时**执行，绝不静默落进去。

- C（AI 生成）：只在真正增加价值的地方用生成位图，通常 1-2 页；生成图要与页面视觉角色匹配，不是通用装饰；生成图里不要带标题、页码、logo 或假 UI 标签。
- B（网络取图）：按 `Pexels（中文 / 国内关键词优先）→ Unsplash → Flickr CC（要纪实感时）→ Wallhaven → 直接搜索` 的顺序取图；下载到任务目录 `assets/`；按用途命名；把来源写进 `assets/SOURCES.md`（一行一条）；**在最终定稿前**把来源告诉用户并询问是否标注。

## Step 7 · Deliver：先给用户看，再问要不要校验

规则的原文是"**Show user first, validate on request**"。每次渲染后自动跑校验会拖长交付窗口，所以默认流程是：

1. 渲染完成后立刻把渲染图 inline 给用户看（绝对路径），附一句说明做了什么。
2. 只问一个问题：**"先你自己看，还是我先自动核查一遍？"**
3. 用户说"我自己看 / 先给我 / no need" → 停在这里，等用户反馈。
4. 用户说"你查吧 / auto-check / yes" → 这时才跑 `node validate-social-deck.mjs <task-dir>`，修掉 FAIL 后重渲再交付；同时在交付信息里提到密度 / 上限类的 WARN。

**绝不**在给用户看图之前静默跑校验——每轮几分钟，而用户往往更快看出问题。

**最终回复应包含**：

- 输出文件夹路径。
- 渲染图（必要时用绝对路径 inline 展示）。
- 尺寸与验证状态的简短说明，或"尚未校验，等你先看"。
- 任何来自网络的图片：来源 URL + 站点 + 用户做出的署名决定。
- Live Photo：`.pvt` 包路径、调试用 `JPG + MOV`、目标平台时长、校验摘要。
- Live Photo 发布提醒：平台限制（小红书 `5s`、公众号 `3s`）与发布路径（把 `.pvt` 作为一个整体 AirDrop 到 iPhone，再从对应 App 发布；桌面 / 网页上传路径一般无法把它识别为可发布的 Live Photo）。
- 如果用户无法走 iPhone / AirDrop 路径（纯桌面、安卓、或平台不支持 Live Photo），**主动提供降级交付**：用同一段 MOV 导出循环 GIF 或静音 MP4，保留运动证据但失去点按播放体验；切换前先与用户确认。
- 任何未解决的风险，例如源图分辨率过低。

## 分支与停顿点汇总

| 时机 | 分支 / 停顿 | 处理方式 |
| --- | --- | --- |
| Step 1 | 用户只给文字 | 一次性问 A / B / C，之后不再劝 |
| Step 1 | 品类落在能力圈外 | 设计前直接说明做不到什么 |
| Step 1 | 内容含不稳定事实 | 浏览核实并在最终回复中给出处 |
| Step 1 | 提供了视频 | 确认平台 → 分类为单视频 / 三连 / 长视频 intake |
| Step 1 | 素材短于目标时长 | 问：更长素材 / 更短 Live Photo / 允许 hold 或慢放 |
| Step 1 | 视频重点区域不明确 | 给裁切方案，让用户确认后再执行 |
| Step 5 | 长视频素材 | 先做稀疏抽帧诊断，再问修剪 / 倍速 / 拆分 / 指定时间段 |
| Step 5 | 拿到首帧静态预览 | 通过后才能渲染 MOV |
| Step 7 | 渲染完成 | 先给用户看图，问一句是否自动核查 |
| Step 7 | 用户无法手机端发布 | 确认后降级为 GIF / 静音 MP4 |
