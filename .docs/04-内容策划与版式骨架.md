# 04 · 内容策划与版式骨架

本文档负责把 skill 在「写什么 / 排什么骨架 / 怎么检查」这一层沉淀下来的经验讲透。读者已经知道 skill 的视觉系统（Editorial / Swiss / Warm Gold）、平台规格和渲染命令，本篇集中讨论：内容压缩策略、11 个小红书品类的路由、平台画板参数、40 个版式骨架的选用与硬约束、以及交付前的密度 / 排版 QA 清单。文中所引数据均来自 `references/` 目录下的同名文档，未在文档中出现的内容一律不补。

## 1. 内容策划：从原文到卡片

### 1.1 压缩阶梯（Compression Ladder）

`references/content-planning.md` 给出了一份从原文到画面文案的五层压缩路径，每一层都要比上一层短：

1. 核心论点（Core claim）：一句话。
2. 观众收益（Viewer promise）：读者滑这套图能拿到什么。
3. 章节地图（Section map）：4-8 个想法。
4. 单页钩子（Page hooks）：短、具体、不抽象。
5. 画面片段（Body fragments）：只保留能解释视觉的词。

总原则：**图集不是把原文搬上画布**，而是给原文做视觉大纲，让读者看了图想去读正文。

### 1.2 封面钩子的句式

封面只放钩子，不放完整论点。可用句式（直接借用自 `references/content-planning.md`）：

- 「终于有 Mac 版了」
- 「新手别急着买」
- 「这个功能真的改变用法」
- 「我替你踩过坑了」
- 「先看这 5 个点」
- 「不要被装备带着走」
- 「从此不用手动 ...」

要避免：过长且完整的小标题；空泛、找不到具体对象的 hype；一张封面上塞多个不相干的论点。

不同品类的封面落点也不同，文档里的偏好是：

- 品类更新（product update）：先讲用户感知的改变，再讲功能名。
- 户外（outdoor）：先讲身体感受——热、湿、滑、重、暴露、迷路、冷。
- AI / 工具：先讲工作流的变化——更快抓取、更少手动、跨应用自动化、可编辑的产物。

### 1.3 拆页与页数策略

小红书图文（Rednote / Xiaohongshu）的页数由字数决定（见 `references/content-planning.md`）：

| 原文长度 | 推荐图集页数 |
| --- | --- |
| 600-1000 中文字 | 5-7 页 |
| 1000-1800 中文字 | 7-9 页 |
| 特别长的原文 | 压缩到 8-10 页，其余进正文/正文区 |

如果多张页面下半部留白明显，应合并相邻页，或改成功能模块（checklist / 对比 / 引用 / 图片证据）。

微信端则走另一套规则（见 `references/platform-specs.md`）：永远出 21:9 主封面 + 1:1 方形封面的组合，两个尺寸都要在同一个 HTML 文件里搭好，不能直接把长标题挤进 1:1，也不能把 21:9 当成 1:1 的素材去裁切。

### 1.4 文案压缩原则

- 标题要平、要快。避免「背景介绍」这种抽象标签，除非这一页真的是背景页。
- 用动词和后果：高帮鞋会让脚更闷，比「鞋子选择」有效。
- 段落要短。`references/layout-recipes.md` 的 M03 已经明说：标题 + 1 段时，应该换成 M04 Pull Quote 或折进 M11 Marginalia，而不是硬塞进 M03。
- 单页只讲一件事；标题中文 12-30 字为宜（见 `references/platform-specs.md`）。
- 文末 / 角标 / kicker（页眉小标签）可重复使用：`AI TOOL / UPDATE / 2026`、`SUMMER HIKING / BEGINNER GUIDE`、`03 / 08`、`DO`、`DON'T`、`WHY`、`NOTE`。它们是定位工具，不要变成装饰。

### 1.5 微信方形封面的短标题压缩

做 WeChat 1:1 封面时，要把 21:9 的长标题再压缩一次（见 `references/platform-specs.md`）：

- 保留核心对象 + 最强动作。
- 中文 4-10 字；一行挤不下就拆两行短句。
- 删掉解释、从句、长定语。
- 永远不要把长标题直接搬进 1:1。

文档里给的例子：

```text
长标题：开源了一个 Skill，让 AI 接管你屏幕边那张便签纸
方标题：AI 接管便签纸

长标题：Codex 史诗级更新，体验爆炸提升
方标题：Codex 大更新
```

### 1.6 区分「观众可见文案」与「生产术语」

这是 `SKILL.md` Step 4 Plan Pages 的硬要求：观众能看到的文字要描述用户的真实场景，不是生产方法。

- 可以写进标题 / 钩子 / 正文：用户的场景、结果、动作、产品名。
- 不能写进画面文案，只能留在计划、文件命名、QA 备注、交付小结里：`3s`、`5s`、`Live Photo`、`triple collage`、`information budget`、`long-video intake`、`speed-up`、`highlight detection`、`one action point`、`layout template` 等。

落版前，要把每个显示出来的标题按真实读者再读一遍；如果听起来像任务要求，就换成场景化表达。

### 1.7 Image-Led 序列（图多内容的特殊处理）

当用户给到了多张高质量生活类照片（旅行 / 户外 / 自家成菜 / 家居 / 情感场景），按 `references/content-planning.md` 的 Image-Led 序列处理：

```text
P1   M16 Image-Led Cover    ← 单张最强照片，全幅出血，标题克制
P2   S11 / M05 / M10         ← 文字密度页：ledger / checklist / 小数据，让眼睛歇一下
P3   M02 Field-Note Photo    ← 次强照片，画框里，给一句说明
P4-N M02 / M11               ← 更多田野笔记或 marginalia 散文
P_last  M07 / M04            ← 收尾：closing note 或 pull quote
```

硬规则：**不能两张 M16 紧挨**。全幅出血封面之后必须先来一页文字，否则两张大图连读像是「作者没想好用哪张」。

这条不适用：新闻 / 教程 / 数据 / 评测——它们的封面是钩子文字，不是照片；只有一张能用的照片时，M16 当 P1，P3-P4 顶多出现一次 M02，不要硬凑图。

Swiss 模式的产品 / 上新帖：照片是产品渲染或 UI 截图，不是生活照；走 S08 Image Hero，而不是 M16。

## 2. 11 个小红书品类的路由

`references/category-cookbook.md` 给 11 个常见小红书品类做了路由，每个品类都标了 What we can do、Style mode、Recipes、Text scheme、Image source、Common pitfalls。本文只做路由摘要和「能力圈边界」，具体每个品类的细节请回到原文。

### 2.1 三档能力圈（Capability Circle）

skill 能稳定端到端产出（文字 + 结构 + 图片故事均由我们交付）：

- 旅行
- 职场
- 推荐（在用户明确子类型后）

skill 在文字 / 结构上强，但图片故事需要用户提供或来自有源库：

- 游戏、影视
- 美食（食谱方向）
- 彩妆（教程方向）
- 健身
- 家居
- 穿搭（精选方向）

明确在能力圈外（不能稳定产出，需要直接 push back）：

- 美食菜品大片摆盘 / 餐厅评测（除非用户现场桌拍）
- 穿搭日常 OOTD 全身（无法生成或征集人体摄影）
- 情感梦核 / 氛围感装饰风（与 Editorial / Swiss 都不兼容）
- 任何高饱和 Y2K / 千禧辣妹 / 哥特萝莉 / kawaii 装饰风
- 纯摄影展示帖（图片本身就是全部产物）

落在「能力圈外」时，要在 intake 阶段说清楚能做什么、不能做什么，不能默默换一个 layout 假装能做。

### 2.3 Live Photo 场景路由（来自 `references/category-cookbook.md` 的 Live Photo Scene Library）

Live Photo 不是单独品类，而是一种「运动作为证据」的卡片形式。常见场景与建议形式：

| 场景 | 用户痛点 | 运动价值 | 建议 Live Photo 形式 |
| --- | --- | --- | --- |
| 游戏攻略 | 静态截图无法说明节奏 / 路线 / 操作时机 | 关键动作 + 成功状态 | 单条 `5s`；三个策略或阶段 → 三连拼图 |
| 产品更新 | 静态截图缺「怎么用」证据 | 触发 → 交互 → 结果 | 单条 `3-5s`；三个功能或产物 → 三连拼图 |
| 教程技巧 | 分步截图太碎 | 一个关键动作或易错步 | 单条 `3-5s`；长视频应剪不要整段压 |
| AI 模型测试 | 静态结果缺过程 / 可信度 | prompt / 过程 / 结果 | 三连拼图；单一清晰生成路径用单条 |
| 旅行攻略 | 漂亮地点照有氛围无过程 | 抵达 / 路线 / 移动 / 现场感 | 单条 `5s`；避免纯风景循环 |
| 生活方式 / 打包 / 居住 | 产品或物件照太摆拍 | 真实拿取 / 打包 / 拆封 / 使用 | 单条 `5s`；checklist 风格 → 三连拼图 |
| 电商种草 | 商品照缺触感 / 比例 / 状态 | 触摸 / 旋转 / 试穿 / 前后 / 细节 | 单条 `3-5s`；细节 / 比例 / 结果 → 三连拼图 |
| 健身动作 | 单个姿势不能说明轨迹 | 幅度 / 节奏 / 修正 | 单条 `3-5s`；错 / 修 / 结果 → 三连拼图 |
| 美食手作 | 成品照缺满足感过程 | 倒 / 搅 / 切 / 组装 / 融化 / 收尾 | 单条 `3-5s`；不在一条 Live Photo 里讲完整食谱 |
| 家居改造 | 静态前后对照断片 | 过渡或实操动作 | 单条；前 / 过程 / 后 → 三连拼图 |

经验法则：

- 一个动作点 → 单条 Live Photo（小红书 `5s`，微信 `3s`）。
- 一个小过程 → 单条 `5s`，可适度加速。
- 三个并列结果 / 视角 / 阶段 → 三连拼图。
- 长序列或解说重的内容 → 先诊断：剪、拆、或建议改用普通视频 / GIF。

## 3. 平台规格：比例 × 像素 × 安全区 × 命名

平台规格集中在 `references/platform-specs.md`。这里只列出对内容策划直接相关的参数。

### 3.1 小红书 / Rednote

- 默认尺寸：`1080 × 1440`，比例 `3:4`。
- 导出格式：文字多的用 PNG；只有照片且关心文件大小时才用 JPEG。
- 安全区：
  - 左右留白 `72-96 px`。
  - 顶部留白 `72-112 px`。
  - 底部留白 `80-120 px`。
- 推荐结构：1 张封面 + 4-8 张内容页；如文章需要，1 张总结 / checklist。
- Live Photo：最长 `5s`，保持 `1080 × 1440` / `3:4` 与同一安全区。
- 文件命名（强制）：

```text
output/xhs-01-cover.png
output/xhs-02-<topic>.png
output/xhs-03-<topic>.png
...
```

### 3.2 微信公众号封面（成对出现）

21:9 主封面：

- `2100 × 900`，比例 `21:9`。
- 主文章封面；接近完整的标题 + 副标题 + 一个强视觉证据。
- 标题放在 center-left 或明确的安全带里；中间不能空。

1:1 方形封面：

- `1080 × 1080`，比例 `1:1`。
- 短标题，大字号，居中。
- 默认不放图，默认不放副标题。
- 强对比、留白充足。

文件命名（强制）：

```text
output/wechat-21x9-cover.png
output/wechat-1x1-cover.png
output/wechat-cover-pair-preview.png
```

公众号封面要在同一个 HTML 文件里搭好一对，再加一个组合预览区域（`wechat-pair-preview`），便于视觉比对。

### 3.3 微信公众号文章 Live Photo

实测截至 `2026-07`：

- iPhone 端上传可在公众号文章编辑中保留 Live Photo。
- 网页端上传没有 Live Photo 入口。
- 时长 ≤ `3s`。
- 发布路径：把 `.pvt` 包作为一个项目 AirDrop 到 iPhone，再在 iPhone 公众号编辑页上传。
- 若发布方只能用桌面 / 网页路径，不要硬撑 Live Photo，改导 GIF / 短片兜底。

WeChat 文章正文卡用与小红书一样的 `3:4` 标准卡。

### 3.4 截图与照片摆放规范

- 原图放进 `assets/`。
- `object-fit: cover` 只在裁切安全时用。
- UI 截图、密集文字、代码、表格、应用窗口一律用 `object-fit: contain`。
- `object-position` 必须显式设置：
  - 长 UI / 顶部重要：top。
  - 物件：center。
  - 人像：纵向 `35%-45%`。
- 不要把图贴到画布边缘，除非设计上要出血。

## 4. 40 个版式骨架总表（最关键的部分）

本节是本文档的核心。`references/layout-recipes.md` 共给出 40 个 recipe，分三组：

- Editorial Magazine × E-ink：M01-M16，共 16 个，主导叙事 / 氛围 / 田野笔记 / 引用。
- Swiss International：S01-S12，共 12 个，主导数据 / 矩阵 / 系统 / 工程感。

每个 recipe 都标了「最佳用途 + Minimum density（最小内容承载）」。下表把 40 个 recipe 平铺。Minimum density 一栏是 `references/layout-recipes.md` 里直接给到的硬要求（未明确给出 density 的标「未明确」）。

### 4.1 总表（40 个版式骨架）

| 编号 | 名称 | 最佳用途 | 适合内容 | 文案 / 密度硬约束 |
| --- | --- | --- | --- | --- |
| M01 | Cover: Magazine Issue Cover | 小红书 P1、portrait 社交卡、文章卡片封面 | 任何需要文字主导封面的内容 | 顶部 issue row + 2-4 行 serif 大标题 + 一张占 35%-55% 的大图或照片 + 底部 3-5 点 issue strip |
| M02 | Field Note Photo | 户外、物件、硬件、真实观察 | 用照片作证据的内容 | 大幅纪实照片 + 窄 caption 列或底部 caption 带 + 一句大字号 takeaway |
| M03 | Editorial Essay Split | 解释一个需要细说的观点 | 散文、长论 | 左大标题或 pull quote + 右 2-3 短段；薄规则分栏。Minimum density (3:4)：标题 + 3 短段，或标题 + 2 段 + 编号 footer list |
| M04 | Pull Quote / Thesis | 一个核心句或结论 | 用来制造节奏 | 大字号 quote + 小号源 / 上下文 + 可选小标注。Minimum density (3:4)：唯一允许 ≤60% 画面内容；必须配顶部 kicker、底部 source 行（18-20px mono，距底 ≤15%）和 source 上方 hairline |
| M05 | Checklist / Buying Guide | 小红书实用型内容 | 购物 / 选购 / 操作步骤 | 4-6 行；每行 编号 + 项目 + 后果；可选小图或材质 swatch |
| M06 | Evidence Wall | 多张截图、参考、小图 | 证据墙 | 2x2 或 3 列网格；每图配短 caption；一个大标题解释含义 |

### 4.2 选骨架的总体准则

1. **Style mode 决定分组。** Editorial 走 M01-M16，Swiss 走 S01-S12，Warm Gold 走 G01-G12；不要在同一个图集里混系统，除非用户明确要 hybrid。
2. **封面 vs 内页。** 封面首选 M01 / S01；当用户给了 1+ 张高质量生活照时，封面改用 M16（图主导）或 S08（产品 hero）。瑞士封面很少用 M16，瑞士里没有「生活 hero」这个概念。
3. **内容长度 → 容量。** 单页内容少就走 M04 / M09 / M13；中等走 M02 / M05 / M11；多就 M08 / M11 / S11。
4. **比较 / 对照** 优先 S02；时间序列优先 S11 / M08；流程图优先 S06 / M14；证据截图优先 M10；多图证据墙 M06。
5. **收尾页** M07 / S07 都可以，但要满足各自的 Minimum density（见上表 M07 行）。
6. **段落分隔** 在 7-9 页小红书套图里，第 3-4 页间插一页 M12 Section Divider，给读者一拍安静。

### 4.3 M16 Image-Led Cover 的四种放置模式

M16 是一个特别的封面，因为它把整张画布交给照片。`references/layout-recipes.md` 给出了四种标题放置模式，由 subject map（主体在画面里的位置）决定：

| 模式 | 中文名 | 主体位置 | 标题位置 | tint（仅 Step 4 失败时用） |
| --- | --- | --- | --- | --- |
| A | 顶压底沉 | 主体在中段（脸、峰、hero 物件），上 + 下都空 | 顶部：kicker（0-12% y）；底部：1-2 行标题（72-92% y） | 优先不加。必要时只在底部加 image-toned radial，峰 α ≤ 0.30 |
| B | 侧栏立柱 | 主体占一个干净的纵向列，对侧 ≥40% 宽度安全（主体边缘不规则时不要用 B，改 A 或 D） | 对侧列（≈36-40% 宽）：kicker → 标题 → 副标题 | 优先不加。必要时单侧横向 falloff（45% 60% at 18% 50%），image-toned |
| C | 角落徽章 | 主体几乎占满画布，只有一个角真的空 | 空角块（≤35% 宽 × ≤25% 高）：kicker / 短标题 / meta | 只在该角加 vignette——不要全图压暗 |
| D | 下沉条带 | 宽幅风景 / 氛围场景 / 没有单一主体；底部有大量负空间 | 底部条带 78-92% y：标题 + meta strip；flush-left 或 flush-right（不居中） | 优先不加。必要时底部 radial，image-toned，峰 α 0.20-0.30 |

M16 排版禁用项（来自 `references/layout-recipes.md`）：

- 标题权重 `700+`（M16 要 regular-medium serif，不是粗体）。
- 纯白 `#fff` 文本（用 paper-cream `#f5f1e8`）。
- 标题 `> 120px`（1080 宽画布上）。
- 主标题用 Latin sans（Helvetica / Inter）。M16 属于 serif；sans 只出现在 kicker / meta / mono caption。
- Mode D 把标题居中（始终 flush-left 或 flush-right，要 Kinfolk 的不对称感）。
- 「先用 mask 救一下」。如果照片过不了 quiet-zone 或 light 测，换 M01 或换图，而不是加蒙版。

### 4.4 能改什么 / 不能改什么

可以改：标题文案、kicker 文案、ledger 行数（在硬上限内）、配色（在对应主题 token 内）、行内 padding/gap（在 1-40px / 40-90px 微调阶梯内，见 6.3 节）。

不能改：

- M03 / M04 / M07 / M13 的 Minimum density。
- S09 / S10 / S11 / S12 的硬上限（行数、cell 数、bar 数）。
- M16 的 quiet-zone + light 闸（失败就换 M01 或换图）。
- 标题在 `display` 上的字号下限（Swiss 是「越大越细」、Editorial 是 regular-medium serif，不是 bold）。
- Style identity test 里的视觉标识：Editorial 必须有 atmosphere 层，Swiss 必须只用一种 accent 色。
- 不要为了「自动化密度警告」加装饰条 / 假时间轴 / 编造徽章——这些不属于任何 recipe。

## 5. 3:4 密度硬要求与 Minimum density 逐条查

`references/layout-recipes.md` 与 `references/qa-checklist.md` 对 3:4 画布的密度给了双重约束。

### 5.1 硬性规则（来自 `references/layout-recipes.md`）

- 在 `1080×1440` 卡片上，**内容必须覆盖 ≥ 75% 画布高度**。
- 任何纯空白带 > 15% 画布高度（> 216px）必须有合理理由：hero image 呼吸、单句陈述、首尾留白（上下加在一起 ≤ 15%）。
- 禁用 `<div style="flex: 1"></div>` 把内容挤到垂直居中。Editorial 杂志的空白跨页能消化；社媒卡是单页滚动，居中后读起来像「PPT 少了一块」。
- 每个 recipe 的 `Minimum density:` 行规定了「这一类 recipe 撑满 3:4 所需的最少内容承载」。达不到时：**缩画布（换 1:1）或换 recipe**，不要把欠内容的卡发出去。

### 5.2 4 横带密度检查（来自 `references/qa-checklist.md`）

渲染完之后，对 3:4 的 PNG 做 4 横带检查（每带 360px，对应 0-25% / 25-50% / 50-75% / 75-100%）：

- Filled：有文字 / 图 / 数据 / 规则。
- Justified empty：空，但有理由——hero image 呼吸（M01 / M16）、单句陈述（M04 / M13）、首尾 8% 留白。
- Under-filled：空且没理由。任何单带 > 15% 画布（> 216px）under-filled = fail。

通过条件（必须同时满足）：

1. Filled + Justified empty ≥ 100%。
2. Filled 带覆盖 ≥ 75% 画布高度（≥ 1080px / 1440px）。
3. 不存在两相邻带都「justified empty」（这意味着中间有 > 25% 真空）。

失败时的修法：

- 不要缩画布、不要加装饰 blob。
- 加内容：加 ledger 条目 / 加段落 / 加证据行 / 加 marginalia 列。
- 换 recipe：内容短 → M07 → M04；中 → M03 → M11（加 marginalia 列）；薄 ledger → M08 Tall Ledger（更大行）。

### 5.3 Minimum density 逐条核对表

把 4.1 总表里所有带 Minimum density 的 recipe 抽出来，渲染前先核对一遍：

| Recipe | 硬要求 | 常见失误 |
| --- | --- | --- |
| M03 | 标题 + 3 短段，或标题 + 2 段 + 编号 footer list | 标题 + 1 段——错，应换 M04 或 M11 |
| M04 | 允许 ≤ 60% 画面内容，但必须有顶部 kicker + 底部 source 行（18-20px mono，距底 ≤ 15%）+ source 上方 hairline | 三个 anchor 缺任何一个 → 留白像缺内容 |
| M07 | 标题 + ≥4 ledger 条目（含子行）+ closing 块 | 2-3 条 ledger → 3:4 留白 ~40%；应扩条目或换 M04 |
| M13 | 顶部 kicker（0-12% y）+ 底部 prompt + 底部 metadata strip；ink-flow 背景必须可见 | ink-flow 缺 / kicker 空 → 像「没填满」而不是「冥想感」 |
| M14 | 3-5 步；超过则拆页或换 M05 | 6+ 步 → pipeline 撑不下 |
| M16 | 通过 `references/image-overlay.md` Rule 1 Steps 1-4（quiet-zone + light 双测） | 照片过不了测 → 换 M01 或换图，不要加 mask |

## 6. 交付 QA 检查清单

`references/qa-checklist.md` 给出三类检查：渲染前、渲染后、交付前。下文按这三类整理。脚本规则（R1-R11）由 `validate-social-deck.mjs` 实现，编号引用即可，命令细节由工具链文档负责。

### 6.1 渲染前（HTML 落版阶段）

- 目标尺寸与平台对齐：小红书 `1080×1440`；微信 21:9 `2100×900`、1:1 `1080×1080`；微信 pair preview 在同一 HTML 文件。
- 文件名按 `references/platform-specs.md` 的命名规范固定排序。
- 安全区、字体加载、box-sizing、overflow:hidden 已就位。
- 选择的 recipe 与 Style mode 一致；同一图集内不混系统（除非用户明确要 hybrid）。
- 主题 token 设到 `<html>`：Editorial 选 6 种杂志配色之一；Swiss 选 4 种 accent 之一。
- 选定的 recipe 与品类 routing 一致（见 2.2 节）。
- 文案经过「真实读者视角」通读：没有把生产术语（`3s` / `Live Photo` / `triple collage` 等）写进画面文案（见 1.6 节）。
- 截图 / 照片有 `object-position`，不是默认 `center 50%`。
- 文末 / 角标 / kicker 文本与品牌一致。

### 6.2 渲染后（拿到 PNG）

- 尺寸核对：`sips -g pixelWidth -g pixelHeight output/*.png`（macOS 例子，见 `references/production-workflow.md`）。
- 4 横带密度检查（见 5.2 节）：Filled + Justified empty ≥ 100%；Filled ≥ 75%；不存在两相邻带都「justified empty」。
- Minimum density 逐条核对（见 5.3 节）。
- R1 / R8 报告的 DOM / 视觉溢出：拿到溢出像素量后查 6.3 节梯子。
- R9 报告的标题与下方内容间距（主标题 ≥ 28px，局域标题 ≥ 16px）。
- R3（Swiss bold display）与 R5（4 带密度）由 validator 自动报——FAIL 就改，WARN 要看。
- 截图缩到 360px 宽做缩略图测试：标题仍然清晰。
- 文末 / 角标是否与内容碰撞；如发现 footer 在内容上方，多半是 footer 用 `position: absolute` 而内容在 flex 中长高了，应改成 `margin-top: auto`（`SKILL.md` Non-Negotiables）。
- 文本不溢出、不贴边、不穿出安全区。

### 6.3 溢出修正梯子（来自 `references/qa-checklist.md`）

根据 R1 / R8 给出的像素量，按下面顺序改：

- `1-40 px` 超：把内容组上移一档，或把某个 gap / padding 紧 20-40 px。不要删内容。
- `40-90 px` 超：局部紧 gap / padding，并把其中一个块紧一格。避免砍文案。
- `90-160 px` 超：略缩 display 标题，或压一个段落，再删内容。
- `160 px+` 超：换更高容量的 recipe，合并模块，或有意识地删内容。

修完别忘回看 R8 报告的「bottom whitespace」，避免从溢出一下子跳到大段空白带。一次只动一档，再过一遍 validator。

### 6.4 交付前（用户拿到结果之前）

- 输出路径写在最终回应里。
- 主要封面图在桌面 / Codex 里用绝对路径内联展示。
- 写明做了哪些核验（尺寸、密度、R1/R8/R9）。
- 列出任何已知限制（素材分辨率低、版权未核实等）。
- 凡是从网上取的图（Pexels / Unsplash / Flickr CC / Wallhaven / 直接搜索），源 URL 已写入 `assets/SOURCES.md`；用户对署名 in-image 的决定已落地（已加 / 不加 / 仅单图加）。
- 微信成对封面在 HTML 中有 `wechat-pair-preview`，视觉关系已确认。
- Live Photo 包（`.pvt`）路径、JPG + MOV pair、目标平台时长、AirDrop 发布路径都已写明；微信端如无法走 iPhone，给出 GIF / 短片兜底。
- Validator 的 FAIL 已修；WARN 已读，已决定接受或继续改。
